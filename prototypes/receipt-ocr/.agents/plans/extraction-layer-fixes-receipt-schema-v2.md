# Feature: Extraction layer fixes and receipt schema v2 (Iteration 26, "Plan A")

The following plan should be complete, but validate documentation, codebase patterns and task sanity
before implementing. Pay special attention to the names of existing utils, types and models, and
import from the right files (`api`/`shared` relative imports need `.js`; `client` imports do not).

Paths are relative to `prototypes/receipt-ocr/`. Line numbers are as of commit `a354225`.

## Feature Description

The user ran all 14 golden-set receipts through the deployed app on 2026-10-09 and found at least one
problem on almost every receipt. Tracing each note against the stored results showed that most are
defects or gaps in our own layer, not in the Azure models: correct values flagged as doubtful, false
VAT warnings, values present in the OCR text that no rule reads, and a `subtotal` field with no stable
meaning. This iteration fixes that layer and changes the canonical receipt schema (subtotal removed,
payment method becomes a category). It is the baseline that Plan B (LLM pass and Content
Understanding measurement) will be measured against.

## User Story

As a business user reviewing a scanned Croatian receipt,
I want correct values to stop being flagged, printed values to be read, and fields that mean nothing
to disappear,
so that a warning or an amber field means something is actually wrong and review is faster.

## Problem Statement

Evidence is the 14 hosted rows created 2026-10-09 08:12–09:12 UTC (table `public.receipts`) and the

| `22559270`, `racuntaksi1` | date amber, value correct | Azure confidence 0.57 / 0.69; the QR code agrees with the value |
| `receipt123`, `22559270` | "VAT amounts don't match total" | rule sums base+VAT against total (`warnings.ts:91-107`); `receipt123` has a PNP row stored as VAT, `22559270`'s recap is 0.90 short of the total by the receipt's own print |
| `receiptWithTaxMistake`, `receiptEuroMistake`, `lira_trogir` | payment method missing or garbage | printed under `Način plaćanja:`; no text fallback exists; `lira_trogir` gets `tridesettri € i 10 c` from `PaymentTerm` |

| most receipts | empty buyer block | buyer fields always rendered |

## Solution Statement

Fix the rules at their cause, change the schema once, and make the scoring harness measure what the
user complained about. Decisions were settled with the user in a grilling session (see NOTES, D1–D14);
do not relitigate them.

### Patterns to Follow

**Text fallback** (`croatian.ts`): a `find*` function returns `CroatianMatch | null` with offsets into
the marker-stripped text; `applyTextFallbacks` (`azure.ts:265-284`) fills only an undefined field and
records `{ confidence: null, source: "text" }`; `source-regions.ts:78-96` outlines it from the same
match. A new fallback must be added in **both** places.

**Enum + translated label**: mirror `RECEIPT_STATUSES` (`shared/src/receipt.ts:5-7`) and its parity
test `client/src/i18n/receiptStatuses.test.ts`. Machine codes are English; the client translates.

**Warnings**: stable code + dotted field path, pure function, never gates anything (`/validate` 6.13).

**Read-time conversion, no backfill**: iteration 24 fixed stored wrapped text in `toFormValues`
rather than migrating rows. This iteration does the same at the repository boundary.

**Comments**: explain *why*, citing the receipt that earned the rule (see `croatian.ts:14-24`).

**Anti-patterns**: no positional or per-receipt heuristics (user rule); no comparing confidence across
models (`/validate` 6.22); no editing `shared/src/money.ts`; no `Number()`/`parseFloat` on money
(`/validate` 6.8); no Azure names outside the adapter directory.
